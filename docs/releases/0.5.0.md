This release makes the registry's data more reliable for clients. Service
types are stored and can be curated (modes `open`, `controlled` and
`moderated`), the registry sets the timestamps of services, and the
environments of services come from a configurable allow-list. Some of these
changes are breaking (see below). Deployments of 0.4.0 keep their data:
read the [upgrade
steps](https://cloud-registry.readthedocs.io/en/v0.5.0/upgrading/#from-040)
first, including the check of the stored environments before the upgrade and
the restart after the rollout. See the
[documentation](https://cloud-registry.readthedocs.io/en/v0.5.0/) for details.

## Breaking changes

- API: the registry sets the timestamps of services (`createdAt` when a
  service is registered, `updatedAt` on every registration and update), as
  RFC 3339 date-times in UTC, in milliseconds. Timestamps that users other
  than admins send are ignored (not an error), so they now describe the
  registry's entry, not the deployment of the service as in the GA4GH
  specification. Admins can still set them, e.g., to import services, but
  only as RFC 3339 date-times (`400` otherwise). Services stored before keep
  their timestamps until they are updated (#236, #237)
- API: `GET /services/types` lists the stored service types, also types that
  no service has (yet), instead of the types of the registered services.
  Types stay registered when the services that had them change or are
  deleted, until admins remove them. On startup, the app stores the types of
  the registered services (#235, #241)
- API: the environment of services (`environment`) must be one of the
  values that the deployment allows (`custom.endpoints.services.environments`,
  by default `prod`, `test`, `dev` and `staging`, the values that the GA4GH
  specification suggests; an empty list allows any value). Registrations with
  other values return `400`, naming the allowed values. Stored services with
  other values are still served, but can only be updated with an allowed
  value (or without `environment`); the app warns of them on startup (#239,
  #242)
- Configuration: overlays that give the policies
  (`security.access_control.policies`) as a list must add the new rules
  `add-service-types` (`POST /services/types`) and `list-approvals` (`GET
  /approvals`), or users can't add service types or list pending approvals
  (#235, #241; #238, #244)

## Features

- Service types: `POST /services/types` registers a type, and admins remove
  types that no service has (`DELETE /services/types`, `409 Conflict` for
  types in use). Registering or updating a service with a new type registers
  the type, too (#235, #241)
- Service types: `custom.access_control.service_types` sets who may add
  types: `open` (the default) lets any authenticated user add them,
  `controlled` only admins (other users can only register services with
  stored types), and `moderated` any authenticated user, but the types of
  users other than admins, and the services that have them, are pending until
  an admin approves them (`PUT /services/types/approval`). Pending types and
  services are only shown to admins and to the users who added them or have a
  role on them; `GET /approvals` lists those a user may see. `GET /me` tells
  clients whether the current user may add types (`may_add_service_types`)
  and whether their new types are pending (`service_types_pending`) (#235,
  #241; #238, #244)

## Maintenance

- Workflows and jobs follow the names of all FOCA apps (`ci.yml`,
  `release.yml`, `scan.yml`), with a single required check, `CI passed`.
  Releases are signed by `release.yml` now: see "Verifying images and
  charts" on the Operations page of the documentation (#233, #234)
- Curated release notes are required for every release, and Sourcery skips
  the inputs of rule tests (#248, #251; #227, #228)
