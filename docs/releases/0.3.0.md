# cloud-registry 0.3.0

The first release tagged from Git, with the app image, the Helm chart and
these notes published together. It changes almost everything since the last
deployed version (Helm chart 2, FOCA 0.12, images tagged by date) and the
legacy charts (2.x and 3.0.0): the registry now requires FOCA 0.15.0 (or a
later 0.15 release) and has owner-based access control, unique services,
verifications by admins and a hardened chart and image. Many of the changes
are breaking; read the upgrade steps first.

## Upgrade

**Redeploy with a fresh install and an empty database; don't migrate the
data.** The previously deployed version (FOCA 0.12) accepted tokens of any
issuer and had no ownership checks, so anyone with any OpenID Connect token
could create, change or delete entries: its data can't be trusted. In the new
version, services stored before have no owner, so only admins could manage
them.

1. Optionally, export the registered services as a reference for their
   operators (`GET /ga4gh/registry/v1/services`).
2. Uninstall the release (`helm uninstall <release> -n <namespace>`; this
   deletes the MongoDB volume and data). Releases of the legacy charts can't
   be upgraded anyway: the chart renames its resources and changes the pod
   selectors.
3. Create a Secret with the MongoDB credentials (MongoDB requires
   authentication now; see "Authentication" in `deployment/README.md`).
4. Write the values file of the deployment (see "Configuration" in
   `deployment/README.md`):
   - `host_name`: the public host name (required);
   - `config.security.auth.audience`: the LS Login client IDs of the apps
     that call the registry, e.g., its front end (required);
   - `config.security.access_control.group_mapping`: the admin group mapped
     to the role `admin`, for ELIXIR
     `urn:geant:lifescience-ri.eu:group:elixir:ECP_CLN:ADMIN#aai.lifescience-ri.eu`
     (required, unless `config.custom.access_control.require_admin` is
     `false`);
   - `mongodb.auth.existingSecret`: the name of the Secret;
   - `config.service_info.service`: the service info (e.g.,
     `environment: prod`), which is no longer set via the API;
   - remove `cloud_registry.appName` (use `fullnameOverride` to choose the
     resource names) and `apiServer`, and move any changes made to the
     `app-config` ConfigMap to `config`.
5. Install the chart attached to this release (`cloud-registry-0.3.0.tgz`):
   `helm install <release> cloud-registry-0.3.0.tgz -n <namespace> -f
   values-prod.yaml`. The chart version goes from 4.0.0 (the last chart
   version in the repository) back to 0.3.0, as it now follows the app
   version; that's no problem for a fresh install.
6. Ask the operators to register their services again (`POST /services`);
   they become their owners. Admins verify them (see "Verified services" in
   the README).

To keep the data anyway, dump and restore it as described in "From the
legacy charts" in `deployment/README.md`: the app then adds keys to the
stored services on startup and refuses to start while some have invalid URLs
or are duplicates (see "Duplicate services" in the README), and admins have
to assign owners (`PUT /services/{serviceId}/permissions/{userId}`).

Docker Compose setups keep the data in a named volume now; see the README
(Deployment) to keep using the former bind mount.

## Breaking changes

### API

- Writes need an access token of LS Login (the only trusted issuer by
  default) for one of the configured audiences, and a role: any
  authenticated user can register services (`POST /services`) and becomes
  their owner; owners can update and delete their services and grant the
  roles `owner` and `maintainer` (updates only); admins can do everything.
  Only admins can register services with chosen identifiers (`PUT` of a new
  identifier).
- `POST /service-info` is removed (`405`); the service info comes from the
  config only (`service_info.service`, served by FOCA), and service info
  stored in the database is no longer served. `GET /service-info` is
  unchanged, and its requests are logged as before.
- Services are unique by URL (normalized) and API type (`type.group`,
  `type.artifact`): registering one again, or changing a service to the URL
  and API type of another one, returns `409 Conflict` naming the registered
  service (`serviceId`).
- URLs must be HTTP(S) URLs with a host, without user info, whitespace,
  control or format characters or malformed percent-encodings (`contactUrl`
  can also be a `mailto:` URL); timestamps (`createdAt`, `updatedAt`) must be
  RFC 3339 date-times; strings are limited in length; others return `400`.
- Registering a service (`POST /services`, `PUT` of a new identifier)
  returns `201 Created` with a `Location` header instead of `200`.
- The identifiers `.`, `..` and `types` are rejected (`400`).
- Request bodies are limited to 1 MiB by default (`413 Content Too Large`),
  also chunked ones, before the access token is checked; requests with an
  invalid `Content-Length` are rejected (`400`).
- Errors are problem details, sent as `application/json`, as the GA4GH
  specification declares, for all errors (including authentication, access
  control and unknown paths); `400` responses say why the request was
  rejected.

### Configuration

- Custom configs must apply the config changes of FOCA 0.14 and 0.15
  (e.g., `exceptions.mapping`; see the FOCA release notes and migration
  guides).
- The service info is configured in FOCA's section `service_info.service`
  (its version comes from `service_info.package`); configs setting it in
  `custom.endpoints.service_info` are rejected.
- The size limit of request bodies is FOCA's `server.max_content_length`
  (Helm chart: `config.server.max_content_length`, which also sets the
  limit of ingress-nginx); configs setting `custom.max_content_length`, as
  for images built from `dev` before the FOCA 0.15 upgrade, are rejected.
- Deployments must set `security.auth.audience` and map an admin group to
  the role `admin` (`security.access_control.group_mapping`), or set
  `custom.access_control.require_admin: false`; otherwise, the app refuses
  to start, and the chart fails to render.
- The app refuses to start if the service info is invalid; its `id` is
  required, and the default config no longer sets a version (the app's
  version is served) or timestamps.
- `custom.endpoints.service.api_path` is now a path prefix in front of the
  API base path (e.g., of a reverse proxy), not the API base path itself.
- `custom.endpoints.services.meta_version` is removed; configs that set it
  are rejected.

### Helm chart

- The chart version follows the app version (0.3.0, after 4.0.0 in the
  repository); the chart attached to a release deploys the image of that
  release (`cloud_registry.tag` defaults to the chart's `appVersion`).
- Resource names are derived from the release name, and the pod selectors
  changed, so releases of the legacy charts must be uninstalled (see
  Upgrade). `cloud_registry.appName` is removed (use `fullnameOverride`).
- The chart no longer creates the `app-config` ConfigMap, the config Job,
  its ServiceAccount and RoleBinding, and the `apiServer` value is gone: the
  app config is set via `config`, rendered into a config overlay. `host_name`
  is required.
- MongoDB is pinned to `mongo:7.0` (instead of `mongo:noble`) and requires
  authentication (`mongodb.auth.existingSecret`), with probes.
- Both pods run with restrictive security contexts (non-root, read-only root
  file system, no capabilities) and without service account tokens.
- Rendering fails without an audience, an admin group mapping (unless
  admins are optional), `host_name` or the MongoDB Secret (unless
  authentication is disabled).

### Image

- `latest` is the highest release; images of commits on `dev` are tagged
  `dev` and `sha-<commit>`. Date-tagged images are no longer pushed.
- The image serves the app with Gunicorn (settings via
  `GUNICORN_CMD_ARGS`, in the chart via `cloud_registry.gunicorn`) instead of
  Flask's development server, and no longer contains the app's source in
  `/app`.
- Docker Compose publishes the app on `127.0.0.1` only.

## New features

- Owner-based access control with the roles `owner` and `maintainer`
  (`/services/{serviceId}/permissions`), and `GET /me` with the current
  user's identifier, admin status and roles.
- Verifications of services by admins (`/services/{serviceId}/verification`,
  `GET /verifications`), without changing the GA4GH endpoints.
- Audit logs of role changes, deletions and verifications.
- Helm chart: Ingress with an optional cert-manager certificate, an
  OpenShift Route otherwise, the request size limit for ingress-nginx,
  Gunicorn settings, probes and the standard labels.

See the README and `deployment/README.md` for details, and the merged pull
requests (#83 to #120) for all changes.
