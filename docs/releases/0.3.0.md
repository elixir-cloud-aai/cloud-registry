# cloud-registry 0.3.0

The first release tagged from Git, with the app image, the Helm chart and
these notes published together. It changes almost everything since the last
deployed version (Helm chart 2, FOCA 0.12, images tagged by date) and the
legacy charts (2.x and 3.0.0): the registry now requires FOCA 0.16.0 (or a
later 0.16 release) and Python 3.13 or later, and has owner-based access
control, unique services, verifications by admins and a hardened chart and
image. Many of the changes are breaking; read the upgrade steps first.

## Upgrade

**Redeploy with a fresh install and an empty database; don't migrate the
data.** The previously deployed version (FOCA 0.12) accepted tokens of any
issuer and had no ownership checks, so anyone with any OpenID Connect token
could create, change or delete entries: its data can't be trusted. In the new
version, services stored before have no owner, so only admins could manage
them.

1. Optionally, export the registered services as a reference for their
   operators (`GET /ga4gh/registry/v1/services`).
2. Uninstall the release (`helm uninstall <release> -n <namespace>`; this
   deletes the MongoDB volume and data). Releases of the legacy charts can't
   be upgraded anyway: the chart renames its resources and changes the pod
   selectors.
3. Create a Secret with the MongoDB credentials (MongoDB requires
   authentication now; see "Authentication" in `deployment/README.md`).
4. Write the values file of the deployment (see "Configuration" in
   `deployment/README.md`):
   - `hostName`: the public host name (required);
   - `config.security.auth.audience`: the LS Login client IDs of the apps
     that call the registry, e.g., its front end (required);
   - `config.security.access_control.group_mapping`: the admin group mapped
     to the role `admin`, for ELIXIR
     `urn:geant:lifescience-ri.eu:group:elixir:ECP_CLN:ADMIN#aai.lifescience-ri.eu`
     (required, unless `config.custom.access_control.require_admin` is
     `false`);
   - `mongodb.auth.existingSecret`: the name of the Secret;
   - `config.service_info.service`: the service info of the deployment
     (e.g., `id`, `name`, `organization`, `contactUrl` and
     `environment: prod`; the defaults changed, see "Configuration" below,
     so set the previous `id`, `ELIXIR_CLOUD_SERVICE_REGISTRY_1`, to keep
     it for clients), which is no longer set via the API;
   - remove `cloud_registry.appName` (use `fullnameOverride` to choose the
     resource names) and `apiServer`, and move any changes made to the
     `app-config` ConfigMap to `config`;
   - rename `host_name` to `hostName` and `cloud_registry` to
     `cloudRegistry` (rendering fails while the old keys are set);
   - optionally, enable the app's NetworkPolicy
     (`cloudRegistry.networkPolicy.enabled: true`), with
     `cloudRegistry.networkPolicy.ingressFrom` matching the cluster's
     ingress controller (default: the namespace `ingress-nginx`). MongoDB's
     NetworkPolicy is enabled by default and only lets the app's pods
     connect (see "Network policies" in `deployment/README.md`).
5. Install the chart attached to this release (`cloud-registry-0.3.0.tgz`):
   `helm install <release> cloud-registry-0.3.0.tgz -n <namespace> -f
   values-prod.yaml`. The chart version goes from 4.0.0 (the last chart
   version in the repository) back to 0.3.0, as it now follows the app
   version; that's no problem for a fresh install.
6. Ask the operators to register their services again (`POST /services`);
   they become their owners. Admins verify them (see "Verified services" on
   the API page of the documentation).

To keep the data anyway, dump and restore it as described in "From the
legacy charts" in `deployment/README.md`: the app then adds keys to the
stored services on startup and refuses to start while some of them have
invalid URLs or are duplicates (see "Stored services" on the Upgrading page
of the documentation), and admins have to assign owners
(`PUT /services/{serviceId}/permissions/{userId}`).

Docker Compose setups keep the data in a named volume now; see "Docker
Compose data" on the Upgrading page of the documentation to keep using the
former bind mount.

## Breaking changes

### API

- Writes need an access token of LS Login (the only trusted issuer by
  default) for one of the configured audiences, and a role: any
  authenticated user can register services (`POST /services`) and becomes
  their owner; owners can update and delete their services and grant the
  roles `owner` and `maintainer` (updates only); admins can do everything.
  Only admins can register services with chosen identifiers (`PUT` of a new
  identifier).
- Bearer tokens must be access tokens as per RFC 9068 (`typ` header
  `at+jwt`, as issued by LS Login); other tokens, such as ID tokens, are
  rejected (`401`).
- `POST /service-info` is removed (`405`); the service info comes from the
  config only (`service_info.service`, served by FOCA), and service info
  stored in the database is no longer served. `GET /service-info` is
  unchanged, and its requests are logged as before.
- Services are unique by URL (normalized) and API type (`type.group`,
  `type.artifact`): registering one again, or changing a service to the URL
  and API type of another one, returns `409 Conflict` naming the registered
  service (`serviceId`).
- URLs must be HTTP(S) URLs with a valid host, without user info,
  whitespace, control or format characters, characters that URLs only allow
  percent-encoded (e.g., `<`, `|`) or malformed percent-encodings
  (`contactUrl` can also be a `mailto:` URL); timestamps (`createdAt`,
  `updatedAt`) must be RFC 3339 date-times; strings are limited in length;
  others return `400`.
- Service URLs (`url`) must be `https` URLs by default, as clients send
  access tokens to the registered services; `http` URLs return `400` unless
  allowed (`custom.endpoints.services.url_schemes`, see "Configuration"
  below). Links keep accepting HTTP(S) URLs (`contactUrl` also `mailto:`).
- Registering a service (`POST /services`, `PUT` of a new identifier)
  returns `201 Created` with a `Location` header instead of `200`.
- The identifiers `.`, `..` and `types` are rejected (`400`).
- Request bodies are limited to 1 MiB by default (`413 Content Too Large`),
  also chunked ones, before the access token is checked; requests with an
  invalid `Content-Length` are rejected (`400`).
- Errors handled by the app are problem details, sent as
  `application/json`, as the GA4GH specification declares (including those
  of authentication, access control and unknown paths); `400` responses say
  why the request was rejected. Error responses keep the headers of the HTTP
  errors, e.g., `Allow` (`405`) and `WWW-Authenticate: Bearer` (`401`, with
  `error="invalid_token"` for invalid tokens). Gunicorn rejects malformed
  requests itself (e.g., with an invalid `Content-Length`, or a request line
  or headers over its limits), with HTML error pages.

### Configuration

- Custom configs must apply the config changes of FOCA 0.14, 0.15 and 0.16
  (e.g., `exceptions.mapping`; see the FOCA release notes and migration
  guides).
- The service info is configured in FOCA's section `service_info.service`
  (its version comes from `service_info.package`); configs setting it in
  `custom.endpoints.service_info` are rejected.
- The size limit of request bodies is FOCA's `server.max_content_length`
  (Helm chart: `config.server.max_content_length`, which also sets the
  limit of ingress-nginx); configs setting `custom.max_content_length`, as
  for images built from `dev` before the FOCA 0.15 upgrade, are rejected.
- Deployments must set `security.auth.audience` and map an admin group to
  the role `admin` (`security.access_control.group_mapping`), or set
  `custom.access_control.require_admin: false`; otherwise, the app refuses
  to start, and the chart fails to render.
- The app refuses to start if the service info is invalid; its `id` is
  required, and the default config no longer sets a version (the app's
  version is served) or timestamps.
- The default service info describes the app, not a deployment, with
  placeholders using reserved example domains (RFC 2606): `id` is
  `org.example.cloud-registry` (was `ELIXIR_CLOUD_SERVICE_REGISTRY_1`),
  `organization` is `Example Organization` at `https://example.org`, there
  is no `contactUrl`, `name` is `Cloud Registry` (was `ELIXIR_CLOUD`), with a
  new `description`. Deployments set their own (`service_info.service`); the
  app logs a warning on startup while `id` or `organization` are the
  placeholders.
- `custom.endpoints.service.api_path` is now a path prefix in front of the
  API base path (e.g., of a reverse proxy), not the API base path itself.
- `custom.endpoints.services.meta_version` is removed; configs that set it
  are rejected.
- `custom.endpoints.services.url_schemes` lists the schemes allowed in
  service URLs: `[https]` by default; Docker Compose (`config.dev.yaml`)
  allows `http` too. On startup, the app warns of stored services with
  other schemes; they are still served, but can only be updated with an
  allowed scheme (see "Stored services" on the Upgrading page of the
  documentation).

### Helm chart

- The chart version follows the app version (0.3.0, after 4.0.0 in the
  repository); the chart attached to a release deploys the image of that
  release (`cloudRegistry.tag` defaults to the chart's `appVersion`).
- Values keys are camelCase, following Helm's conventions: `host_name` is
  renamed to `hostName` and `cloud_registry` to `cloudRegistry`; rendering
  fails while the old keys are set.
- Resource names are derived from the release name, and the pod selectors
  changed, so releases of the legacy charts must be uninstalled (see
  Upgrade). `appName` of the legacy charts is removed (use
  `fullnameOverride`).
- The chart no longer creates the `app-config` ConfigMap, the config Job,
  its ServiceAccount and RoleBinding, and the `apiServer` value is gone: the
  app config is set via `config`, rendered into a config overlay. `hostName`
  is required.
- MongoDB is pinned to `mongo:7.0` (instead of `mongo:noble`) and requires
  authentication (`mongodb.auth.existingSecret`), with probes.
- Both pods run with restrictive security contexts (non-root, read-only root
  file system, no capabilities) and without service account tokens.
- A NetworkPolicy lets only the app's pods of the release connect to
  MongoDB (`mongodb.networkPolicy.enabled`, default `true`), if the cluster
  enforces NetworkPolicies; other pods that connected to MongoDB directly
  (e.g., backup jobs) need a NetworkPolicy of their own, or the policy
  disabled.
- Rendering fails without an audience, an admin group mapping (unless
  admins are optional), `hostName` or the MongoDB Secret (unless
  authentication is disabled).

### Image

- `latest` is the highest release; images of commits on `dev` are tagged
  `dev` and `sha-<commit>`. Date-tagged images are no longer pushed.
- The image serves the app with Gunicorn (settings via
  `GUNICORN_CMD_ARGS`, in the chart via `cloudRegistry.gunicorn`) instead of
  Flask's development server, and no longer contains the app's source in
  `/app`.
- Docker Compose publishes the app on `127.0.0.1` only.

### Python

- The app requires Python 3.13 or later, the Python version of the image
  (based on `elixircloud/foca:0.16.0-py3.13`), the only one it is tested
  with.

## New features

- Owner-based access control with the roles `owner` and `maintainer`
  (`/services/{serviceId}/permissions`), and `GET /me` with the current
  user's identifier, admin status and roles.
- Roles on services for groups
  (`/services/{serviceId}/permissions/groups/{entitlement}`, with the
  group's `eduperson_entitlement` URL-encoded): all members of the group
  have the role, e.g., a team group of an ELIXIR node in Perun. Owners can
  grant roles only to groups they are members of (`403` otherwise), admins
  to any group. `GET /services/{serviceId}/permissions` lists the roles of
  users and groups together (`{"group": ..., "role": ...}` for groups), and
  `GET /me` also lists roles through groups (with `group`). Groups count as
  owners: a service may be left with a group as its only owner, which then
  depends on the group's membership in Perun. The base config sets
  `security.access_control.keep_group_subjects: true` for this, so all
  group claim values are used as subjects, besides the admin group mapping.
  All members of an owner group can list the identifiers and names of all
  users with roles on the service, and remove the other owners, so don't
  grant roles to broad groups (e.g., all members of a virtual organization).
  Users removed from a group keep its roles for up to 5 minutes, as FOCA
  caches the user info of each token (see "Group membership changes" on the
  Access control page of the documentation).
- Verifications of services by admins (`/services/{serviceId}/verification`,
  `GET /verifications`), without changing the GA4GH endpoints.
- Audit logs of role changes, deletions and verifications.
- Helm chart: Ingress with an optional cert-manager certificate, an
  OpenShift Route otherwise, the request size limit for ingress-nginx,
  Gunicorn settings, probes, the standard labels and NetworkPolicies (for
  MongoDB by default, optionally for the app: `cloudRegistry.networkPolicy`).
  The Ingress (or Route) routes all paths, including FOCA's permissions API
  for admins (`/admin/access-control/`); see "Ingress" on the Deployment
  page of the documentation to keep it off the internet.

and the [changes since the last deployed
version](https://github.com/elixir-cloud-aai/cloud-registry/compare/19f664f4244ccf4511621c523efa20d827bae87c...v0.3.0)
for all merged pull requests.
