This second release candidate of 1.0.0 moves all additions to the API to
camelCase, also where they are stored, so **it needs a fresh database: data is
not kept, and there is no migration.** It also moves the roles of users to a path
of their own, so that they can't collide with those of groups, adds labels to
invitations and keeps expired invitations for a set time. It is a prerelease, for
testing the release before 1.0.0. **The registry and
[cloud-registry-ui](https://github.com/elixir-cloud-aai/cloud-registry-ui) ship
together: use version `1.0.0-rc2` of the UI with this version.** Read the [upgrade
steps](https://cloud-registry.readthedocs.io/en/v1.0.0rc2/upgrading/#from-100rc1)
first. See the [documentation](https://cloud-registry.readthedocs.io/en/v1.0.0rc2/)
for details.

## Breaking changes

- Fresh database: stored fields and indexes move to camelCase, without a
  migration, from any earlier version. The app refuses to start on data or indexes
  of earlier versions, naming the collections, and no longer adds keys or creators to
  stored services or warns of data of earlier versions on startup (#352)
- API: all fields and query parameters that the registry adds move to camelCase,
  without aliases, so clients must follow (e.g., `registrationRules`,
  `verifiedAt`, `serviceId`, `userId`, `createdBy`, `?includeAccepted=true`). The
  [upgrade steps](https://cloud-registry.readthedocs.io/en/v1.0.0rc2/upgrading/#from-100rc1)
  list them all (#352)
- API: `PUT` and `DELETE /services/{serviceId}/permissions/{userId}` move to
  `/services/{serviceId}/permissions/users/{userId}`, without an alias: the
  former paths return `404 Not Found`, so move API clients in the same upgrade.
  With identifiers that start with `users/`, the former path is the new path of
  the user without that prefix, so stop clients that weren't moved first (#336,
  #337)
- Access control: the rule `owners-change-permissions` moves to
  `.../permissions/users/*`, and no longer covers the roles of groups. Overlays
  that redefine it, or give `policies` as a list, must move it. Setting
  `owners-change-group-permissions` to `null` now stops owners from changing
  roles of groups (#336, #337)
- Invitations: `GET /services/{serviceId}/invitations` no longer lists accepted
  invitations unless asked (`?includeAccepted=true`), now lists expired ones,
  and all invitations have a `status` (`open`, `expired` or `accepted`). Clients
  that show all listed invitations as open must check it (#332, #335)
- Startup: the app refuses to start if the environment of its service info
  (`service_info.service.environment`) isn't one of the values allowed for
  services (`custom.endpoints.services.environments`). The defaults pass; check
  deployments that changed either (#346, #348)

## Features

- Invitations: an optional `label` says what an invitation is for (e.g., who it
  was sent to), returned to those who can list the invitations (#331, #334)
- Invitations: those that weren't accepted are kept after they expire, so that
  owners see who needs a nudge, for
  `custom.access_control.invitations.keep_expired_days` days (default: 30, at most
  365; `0` removes them when they expire, as before), and owners can remove them
  earlier (#332, #335)
- Admins can list the registry among its own services, or remove it
  (`/service-info/listing`): the entry and its service type are built from the
  service info and the public URL, it has no owner, doesn't count for service
  limits, is verified, and is brought up to date when the app starts (#347, #349)
- Access control: users called `groups`, or whose identifiers start with
  `groups/`, can be granted roles and accept invitations, and the namespaces of
  issuers may start with `groups/` (#336, #337)

## Security

- Image: no pip, from FOCA 0.20, so scans no longer report the packages it
  vendors, and `.trivyignore.yaml` has no entries (#350)
- Privacy: kept invitations hold their labels, which may name people, and who
  created them and when, for up to 37 days after they were created by default
  (7 before): check the default against your privacy statement (#332, #335; #338,
  #342)
- Image: the build context excludes more files that can hold secrets (#329, #330)

## Fixes

- `python -m cloud_registry.namespace_subjects --dry-run` leaves the database as
  it is: it no longer sets up the app, which changed indexes and configured rules
  and could keep pods of an older version from restarting. It only counts what is
  stored, and doesn't check the config as startup does (#339, #343)

## Documentation

- Upgrade steps: they add up across versions; the matching version of the UI;
  access control: what kept invitations store, and which identifiers can't accept
  invitations (#338, #342)
- API style: additions follow the style of the spec they extend, and additions to
  spec objects are kept to a minimum and grouped (#352)

## Maintenance

  from the app's image must use uv too (#350)
- Tests: the smoke test checks the moved path on the built image (#340, #344)
- Dependencies: mypy 2.4.1 (#322)
